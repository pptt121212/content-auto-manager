# API 设置

## 这篇文档解决什么问题

这篇文档帮助你真正理解：Yali AI Writer 的 API 设置页不是“填几个接口参数”的技术页，而是整套系统的能力接入中心。主题生成、文章生成、向量能力、搜索资料、网页解析，都会从这里获得执行基础。

如果这一步没做好，后面的页面即使都能点，也很难稳定产出。

---

## 模块用途

API 设置负责管理五类能力接入：

1. **自定义文本 API**
2. **预置 API**
3. **向量 API**
4. **搜索 API**
5. **Jina Reader**

它们共同构成了系统的“能力底座”。

其中最重要的逻辑不是“能不能保存配置”，而是：

- 哪些配置会参与任务轮询
- 哪些配置是全系统唯一
- 哪些配置会影响语义能力一致性
- 哪些配置只在联网资料链路中起作用

---

## 适用场景

你最适合在这些情况下进入 API 设置页：

- 第一次部署插件
- 想接入或替换文本模型服务商
- 想提升任务稳定性，配置多套接口轮询
- 想启用向量、搜索或 Reader 能力
- 发现主题生成、文章生成、召回、去重、结构匹配结果异常，怀疑能力层有问题

## 各标签页怎么理解

### 一、自定义 API

这是最常用的文本模型配置区，适合你接入自己的大模型服务。

当前代码中已明确支持的类型包括：

- OpenAI 兼容格式
- Google Gemini
- Anthropic Claude

你通常会在这里配置：

- 配置名称
- API 类型
- 接口地址
- API Key
- 模型名
- 温度
- 最大 Token
- Top_p
- 是否流式
- 是否激活

#### 这一区的业务意义
它决定系统是否能真正执行文本生成类任务，例如：

- 主题生成
- 文章生成
- 编辑器助手生成
- 某些参考资料整理流程

#### 对运营人员来说最该关心什么
不是参数越多越好，而是先确保：

- 至少有一套可用文本接口
- 模型类型与目标任务匹配
- 激活状态正确
- 连接测试通过

---

### 二、预置 API

这一页更像系统内置渠道管理区。

它的意义通常有两层：

1. 作为一种可直接使用的渠道
2. 作为自定义接口失败时的兜底回退来源

页面中已确认存在的交互包括：

- 渠道选择
- 模型同步
- API Key 填写
- 配额 / 账户信息查看
- 激活控制

#### 适合什么时候用
- 你想快速接入系统已有渠道
- 你想给自定义接口配置一个兜底来源
- 你在追求更高稳定性，而不是只依赖单一接口

---

### 三、向量 API

这是一个非常关键但最容易被低估的标签页。

它不是普通“再加一套模型”这么简单，而是整个系统语义能力的公共基础。它会影响：

- 主题向量生成
- 语义相似度计算
- 主题去重
- 结构匹配
- 品牌资料召回
- 参考资料召回
- 向量聚类
- 内链辅助能力

#### 为什么它通常是“唯一配置”
代码中它以单例配置方式出现，意味着系统默认期待全局语义空间保持一致。

#### 这意味着什么
如果你频繁切换向量模型，旧向量和新向量可能不再可直接比较，结果就会出现：

- 去重变形
- 相似召回偏移
- 结构匹配不稳定
- 聚类质量下降

#### 对运营最重要的建议
文本模型可以多套轮询，向量模型尽量稳定，不要轻易来回换。

---

### 四、搜索 API

这一页负责联网资料获取的前置能力。

当前能确认的主要设置包括：

- 地区
- 最大结果数
- 安全搜索
- 时间范围
- 搜索后端
- 搜索测试框

#### 它影响什么
它不直接写文章，但会显著影响：

- 搜索资料的覆盖面
- 联网召回内容的新旧程度
- 主题或文章参考信息的质量

#### 为什么它很重要
很多人把搜索能力理解成“只是多拿几条结果”，但对于内容系统来说，它更像在决定：

- 你拿到的是不是目标地区语境下的资料
- 你拿到的资料是不是太旧
- 你拿到的内容是否适合继续送给模型处理

---

### 五、Jina Reader

这一页用于网页内容解析。

它的业务位置通常在搜索之后、模型消费之前。作用是把网页转成更适合模型处理的文本结构。

页面里已确认的关键项包括：

- Reader API Key
- 黑名单设置（域名或关键词过滤）

#### 它适合解决什么问题
- 原网页内容过于杂乱
- 搜索结果需要进一步正文抽取
- 某些来源质量不稳定，需要先过滤

## 关键设置怎么用通俗的话理解

### 是否激活
只有激活的配置才会真正参与任务执行。配置保存成功不等于会被系统使用。

### API 类型
它决定请求格式和参数结构。不是标签名而已，填错后哪怕接口地址和 Key 正确，也可能无法正常调用。

### 模型名称
它决定实际调用哪个模型，也影响风格、速度、成本和输出上限。

### temperature / max_tokens / top_p
它们不是“技术选项展示”，而是直接影响：

- 输出发散程度
- 输出长度
- 成本
- 稳定性

### 向量模型
它决定整套系统的语义空间。越稳定，越利于长期使用和结果一致。

### 搜索地区 / 时间范围 / 安全搜索
它们直接影响你召回资料的可用性和质量，不只是“搜索页面显示起来更像哪个地区”。

### stream
会影响请求方式和超时表现，尤其在长内容生成或接口稳定性不高时更敏感。

## 标准操作任务

### 场景一：第一次初始化
1. 先配置至少一套自定义文本 API
2. 测试连接成功
3. 视需要配置预置 API 作为兜底
4. 如果要用语义能力，再配置向量 API
5. 如果要做搜索资料，再配置搜索 API 与 Reader
6. 回到主链路验证是否能成功生成主题或文章

### 场景二：接口不稳定，需要提高成功率
1. 检查当前激活的文本 API 是否过少或质量差异过大
2. 增加更稳定的接口组合
3. 补充预置渠道作为失败回退
4. 对关键配置做连接测试
5. 观察后续主题与文章任务成功率

### 场景三：去重、召回、结构匹配结果突然变差
1. 先检查向量 API 是否被替换或重配
2. 确认不是语义空间发生变化
3. 再检查下游阈值或召回逻辑
4. 不要只盯文章任务结果看

## 做完之后，你应该看到什么

- 至少一套可用文本模型处于激活状态
- 如果启用语义能力，向量配置稳定存在
- 如果启用搜索链路，搜索 API 和 Reader 已可用
- 后续主题、文章、召回类功能具备可执行条件

---

## 常见误区

### 误区一：只保存，不测试
很多配置看似已经填完，但真正连通性并不一定成立。至少关键接口要做一次测试。

### 误区二：激活太多质量差异过大的文本接口
这样会让输出风格和稳定性漂移明显，不利于稳定生产。

### 误区三：频繁切换向量模型
这会破坏语义一致性，影响去重、结构匹配、召回和聚类。

### 误区四：把搜索和 Reader 当成可有可无
如果你希望资料链路更完整，它们往往是结果质量差距的重要来源。

---

## 上下游关系

### 上游
API 设置本身是能力接入层，通常没有更硬性的业务上游。

### 下游
它会被多个模块共同消费，包括：

- 主题任务
- 文章任务
- 编辑器助手
- 搜索物料
- 向量相关能力
- 结构匹配与智能优化
- 品牌资料 / 参考资料召回

### 与其他核心模块的关系
- **发布规则**定义“怎么生成”
- **API 设置**定义“能不能生成、用什么生成”
- **规则管理 / 主题任务 / 文章任务**是具体消费这些能力的业务页面

## 给 AI / 技术读者的结构化摘要

### purpose
api settings is the capability-ingress page for text generation, predefined channels, vector model, search backend, and reader parsing.

### entry
- menu label: API设置
- slug: `yali-ai-writer-api`
- tabs: custom, predefined, vector, search, reader

### key model layers
- text APIs: multi-config, rotatable/activatable
- predefined APIs: built-in channels and fallback options
- vector API: singleton semantic foundation
- search API: retrieval configuration
- reader API: page-to-text parsing and blacklist filtering

### operator priorities
first make text generation usable, then stabilize vector config, then add search and reader if retrieval workflows are needed

### major risks
saving without testing, over-activating inconsistent text providers, changing vector model too often

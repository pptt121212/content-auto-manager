# 仪表盘

## 这篇文档解决什么问题

这篇文档帮助你理解：Yali AI Writer 的仪表盘不是一个“好看但可有可无”的首页，而是一个用于快速判断系统是否健康、主链路是否顺畅、缓存和任务是否需要人工干预的总控观察页。

如果你刚接手插件，仪表盘能帮你迅速知道下一步该进哪个页面；如果你已经在稳定生产，它则是你每天用来判断系统状态的第一站。

---

## 模块用途

仪表盘是插件后台的顶层入口页面，对应主菜单中的第一页。它承担三个核心职责：

1. **导航与总览**：帮助你在最短时间内理解当前系统整体运行状态
2. **运营观察**：集中展示主题、文章、规则、任务、向量、配图等关键统计
3. **维护操作**：提供语言保存、缓存刷新、队列清理和任务数据清理等运维型动作

它不直接创建主题，也不直接生成文章，但它能告诉你当前更应该去“API 设置”“发布规则”“主题任务”“主题管理”还是“文章任务”。

---

## 适用场景

你最适合在这些场景进入仪表盘：

- 第一次接手插件，想先看系统目前大致运行到什么状态
- 每天开始运营前，先快速看主题和文章链路是否健康
- 发现文章生成速度异常、任务堆积或统计明显不对时
- 需要清理队列、批量清理任务遗留数据时
- 想检查分类缓存、向量覆盖率、主题状态分布是否异常时

## 页面结构

根据当前仓库中的视图与脚本，这个页面主要由下面几块组成。

### 1. 页面头部与总览区
这是整个后台的“健康度第一眼”。通常你会先看到页面标题和概览信息，用来判断当前系统是否已经具备继续生产的条件。

### 2. API 配置状态
这一区块回答的是：**模型与服务接入是否处于可用状态。**

对于运营人员来说，它的意义不是看“技术字段”，而是快速判断：

- 当前是否已经配置文本模型
- 是否已经准备好支撑主题或文章生成
- 是否还缺关键能力接入

如果这里明显不完整，就不建议往下继续做主题或文章操作。

### 3. 内容生产统计
这一区块更偏业务视角，主要帮助你判断系统当前内容生产的规模和节奏，比如：

- 主题数量情况
- 文章任务情况
- 规则数量
- 已发布文章数量
- 高优先级主题情况

它适合回答一个问题：**这套系统是在“刚搭好”，还是已经进入“稳定生产中”。**

### 4. 任务执行状态
这一块更偏执行层观察。重点不是绝对数字，而是状态分布是否合理。

如果你发现：

- 某类任务长时间不下降
- 失败明显偏高
- 某个阶段卡住

那就说明你应该去对应的任务页或上游页进一步排查。

### 5. 系统设置
仪表盘不是只负责看，它也提供部分全局维护动作。当前已确认的包括：

- 保存插件界面语言
- 与分类缓存有关的动作
- 与队列清理有关的动作
- 与批量清理任务数据有关的动作

这类动作更像“运维工具”，不要当成日常内容生产主操作，但在状态异常时很关键。

### 6. 状态分布区
页面会展示与主题、文章、向量、队列等有关的分布信息。它特别适合拿来做“异常信号发现”：

- 主题是不是大量卡在某个状态
- 文章状态是不是与预期不符
- 向量覆盖率是不是太低
- 队列是不是堆积在某个类型上

### 7. 缓存与队列相关区
这一块通常是人工介入最容易发生的地方。特别是：

- 分类缓存需要刷新
- 队列有明显残留
- 旧任务数据需要清理

这些操作都属于“恢复系统干净状态”的动作。

## 页面上常见的可见操作

根据当前代码，仪表盘上能确认的操作包括：

- 保存插件 UI 语言
- 刷新或生成分类缓存
- 清理队列
- 批量清理选中的任务数据
- 打开相关确认弹窗后再执行敏感操作

这些动作说明：仪表盘不是单纯统计板，它同时承担了一部分后台维护入口的职责。

## 关键设置怎么理解

### 插件界面语言
它影响的是插件后台界面的显示语言，而不是文章生成语言。

很多新手会把它和“发布语言”混淆。要记住：

- **仪表盘里的语言设置**：更偏后台使用体验
- **发布规则里的发布语言**：更偏模型输出语言和产物语言

### 分类缓存
它影响分类相关页面的可用性与选择体验，尤其是在规则、主题和发布规则里涉及分类选择时更重要。

如果分类刚调整过，或页面里分类选择结果看起来不对，优先考虑先刷新缓存。

### 队列清理 / 任务数据清理
它们是恢复型操作，不是日常高频动作。

适合在这些情况下使用：

- 有明显挂起或残留任务
- 测试阶段留下了很多无用任务记录
- 任务与统计数据不一致，需要人工清理环境

不适合在你还没确认任务真实状态之前随意使用。

## 标准操作任务

### 场景一：每天开始工作前做系统总览
1. 打开仪表盘
2. 看 API 配置状态是否完整
3. 看主题任务与文章任务是否有异常积压
4. 看主题与文章状态分布是否异常
5. 如果有问题，再跳转到具体页面处理

### 场景二：发现分类相关结果不稳定
1. 打开仪表盘
2. 检查分类缓存区
3. 执行分类缓存刷新
4. 再回到发布规则、规则管理或主题管理页复查

### 场景三：发现任务残留或测试数据很多
1. 在仪表盘先看任务与队列分布
2. 进入清理动作前确认不是仍在执行中的真实任务
3. 使用清理队列或批量清理数据动作
4. 再回到任务页确认状态是否恢复

## 做完之后，你应该看到什么

- 系统整体统计更符合当前实际情况
- 分类缓存相关问题得到缓解
- 队列或任务遗留减少
- 你能更明确判断接下来要去哪一个核心页面继续工作

如果做完后仍看不出问题在哪，说明真正的原因多半在更具体的模块中，而不是仪表盘本身。

---

## 常见误区

### 误区一：把仪表盘当成主要操作页
仪表盘更适合“判断”和“维护”，不是主生产动作的核心入口。真正的生产通常还是在 API 设置、发布规则、规则管理、主题任务、主题管理和文章任务里完成。

### 误区二：看统计不看趋势
单次打开看到的数字本身意义有限，更关键的是：

- 是否长期堆积
- 是否与预期规模明显不符
- 是否集中卡在某个状态

### 误区三：一遇到异常就先清理
清理动作很有效，但不应该代替排查。很多异常的根因在上游配置，而不是队列残留本身。

---

## 上下游关系

### 上游
仪表盘本身没有严格上游，它更像所有核心模块的总览出口。

### 下游
它不会直接产生产物，但会把你引向真正需要操作的页面，例如：

- API 设置
- 发布规则
- 规则管理
- 主题任务
- 主题管理
- 文章任务

### 横向依赖
它横向读取并展示多个模块的数据状态，包括：

- 主题任务
- 文章任务
- 规则
- 发布规则
- 向量覆盖
- 自动配图文章
- 队列状态

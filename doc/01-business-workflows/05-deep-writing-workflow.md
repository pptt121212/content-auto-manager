# 深度写作与浏览器扩展流程

## 这条流程在业务里解决什么问题

深度写作流程不是为“更快批量出文”设计的，而是为另一种更重、更长、更依赖浏览器扩展执行的写作方式设计的。它适合那些已经确认值得投入单篇资源的主题。

这里先讲最重要的边界：

**深度写作不是标准文章生成的增强开关，也不进入现有文章任务队列。**  
它是一条单独的跨端流程，插件负责发起、占位、接收回调和创建草稿，真正的写作执行发生在浏览器扩展本地队列中。

## 谁最常用，什么时候用

最常用这条流程的人通常是：

- 重点内容负责人
- 需要更重写作链路的管理员
- 愿意接受单篇较长执行时间的人

最适合使用的时机，是你已经在主题管理页完成筛选，确认某些主题值得走更重的单篇写作路径，而不是直接进入标准批量文章生成。

## 开始前要准备什么

这条流程的前置条件比标准文章生成更明确：

1. 目标主题已经在主题管理页，并且仍是 `unused`
2. 鸭梨 AI 浏览器扩展已经安装并可用
3. 你准备在执行期间保持扩展开启
4. 图像 API 已经配置，因为确认提示里明确说明深度写作文章会自动配图
5. 你接受单篇执行时间通常在 5 到 30 分钟之间

## 页面入口和发起路径

发起入口在：

- `鸭梨AI写手 > 主题管理`

在这个页面，勾选主题后，可以点击 `深度写作`。

## 第一步：发起前先看清确认提示

点击 `深度写作` 后，页面会弹出确认提示。已确认提示内容至少包括：

- 需要打开鸭梨 AI 浏览器扩展
- 每篇文章约执行 5 到 30 分钟
- 执行期间不要关闭扩展
- 完成后文章会回到 WordPress
- 结果以草稿形式回写
- 文章中会自动配图，因此要提前配置图像 API

这一步的意义很重要，它在告诉你：这条流程不是即时返回型任务，而是跨插件与扩展的托管写作。

## 第二步：只有可用主题才能进入深度写作

主题管理页已经把这个约束落实到交互上了。`queued` 和 `used` 主题会被禁用勾选，只有可用主题才允许发起深度写作。

业务意义很直接，系统不允许同一个主题同时被多条写作链路重复占用。

## 第三步：插件侧发起时到底做了什么

当管理员提交 `deep_writing` 后，插件侧会先校验请求，再逐个处理被选中的主题。对每个主题，已确认会做这些动作：

1. 读取主题数据
2. 检查主题当前必须是 `unused`
3. 读取发布规则中的补充字段
4. 解析 SEO 关键词与参考资料
5. 组装扩展可执行的任务载荷
6. 将任务加入插件到扩展的任务通道
7. 把主题状态更新为 `queued`
8. 记录主题与扩展任务 ID 的映射关系

所以，插件在这里扮演的不是写作者，而是任务分发者和占用状态维护者。

## 第四步：真正执行发生在浏览器扩展本地

深度写作队列不是直接靠 WordPress 数据库执行的，而是持久化在浏览器本地存储中。

### 扩展本地执行状态
已确认包括：

- `pending`
- `running`
- `interrupted`
- `completed`
- `deleted`

### 同步状态
还会维护另一组同步状态：

- `pending`
- `syncing`
- `synced`
- `sync_failed`

### 这意味着什么
执行成功和同步成功不是一回事。正文可能已经写完，但草稿未必已经成功写回 WordPress。

## 第五步：扩展是严格串行执行的

这条流程的一个重要特点，是扩展侧采用严格串行执行，同一时间只允许一个 `running` 任务。

这会带来两个实际影响：

1. 任务更稳定，不容易并发打架
2. 你不能把它当成标准文章生成那种快速批量并行流程来理解

如果你一口气发起多个深度写作主题，它们会排队，而不是同时在插件内全部开跑。

## 第六步：扩展侧正常执行路径怎么理解

扩展启动时，会先把遗留的 `running` 任务转成 `interrupted`，避免异常退出后留下假运行状态。

单个任务正常执行时，可以按下面顺序理解：

1. 取下一个待处理任务
2. 把状态改为 `running`
3. 创建写作编排器
4. 注入参考资料
5. 执行完整写作流程
6. 成功后把本地执行状态改为 `completed`
7. 保存结果快照
8. 再进入 WordPress 草稿同步流程

这里最容易误解的一点是，`completed` 只代表正文本地写完，不代表 WordPress 草稿一定已经写入成功。

## 第七步：草稿是怎么同步回 WordPress 的

自动同步发生在本地正文写作成功之后。扩展会：

1. 取标题、正文和封面图等结果
2. 将同步状态改为 `syncing`
3. 调用插件回调接口
4. 最多自动重试 3 次
5. 成功则标为 `synced`
6. 三次仍失败则标为 `sync_failed`

插件回调成功后，会完成这些结果：

- 创建 WordPress 草稿
- 写入关联元数据
- 更新主题状态为 `used`
- 清理影子状态和主题任务映射

这时才算这条链路真正闭环完成。

## 第八步：最关键的业务分支是什么

### 分支一：正文写完了，但同步失败
这是深度写作里最关键的异常分支。

此时扩展本地执行状态已经是 `completed`，但同步状态会变成 `sync_failed`。插件不会把主题恢复成 `unused`，因为正文其实已经生成完成，只是草稿还没成功写回 WordPress。

这一步很关键，说明系统在优先保持“主题占用状态”和“已完成正文”的一致性，而不是简单回滚。

### 分支二：扩展异常关闭或执行中断
扩展下次启动时，会把遗留 `running` 任务改为 `interrupted`，用户可以再决定恢复或删除。

### 分支三：用户删除中断任务
扩展会调用 release 接口通知插件释放占用。插件收到后，会把主题状态恢复为 `unused`，并清理影子状态和映射关系。

## 什么时候更适合用深度写作，而不是标准文章生成

更适合深度写作的场景有：

- 你关心单篇主题，而不是批量吞吐
- 你能接受每篇较长执行时间
- 你愿意配合浏览器扩展完成跨端执行
- 你希望结果先以草稿方式回到 WordPress，再人工校对

如果你的目标是规模化监控、快速重试和批量生产，标准文章生成通常更合适。

## 常见失败点

### 1. 没打开扩展就发起
这会直接破坏这条流程的执行前提。

### 2. 执行中关闭扩展
容易造成中断，后续任务会进入 `interrupted` 分支。

### 3. 误以为 completed 就等于已入库
实际上还要看同步状态是不是 `synced`。

### 4. 图像 API 没配置
确认提示已经明确提到深度写作文章会自动配图，所以这不是可忽略前置。

## 完成后应该看到什么结果

这条流程结束后，理想结果是：

1. 扩展本地任务完成
2. WordPress 里生成对应草稿
3. 主题状态从 `queued` 变成 `used`
4. 插件和扩展之间的映射与占用状态被正确清理

## AI / 技术结构化摘要

### 业务定位
- 深度写作是主题后的独立重写作链路
- 不进入现有文章任务队列
- 由插件发起，由浏览器扩展本地串行执行，再回调创建 WordPress 草稿

### 页面路径
- 发起：`鸭梨AI写手 > 主题管理 > 深度写作`

### 插件侧职责
- 校验主题可用性
- 组装任务载荷
- 更新主题为 `queued`
- 维护主题与扩展任务映射
- 接收回调创建草稿
- 在成功时将主题标记为 `used`
- 在删除释放时恢复为 `unused`

### 扩展侧职责
- 本地队列持久化
- 严格串行执行
- 中断恢复
- 本地结果保存
- 草稿同步与重试

### 状态体系
- 扩展执行状态：`pending` `running` `interrupted` `completed` `deleted`
- 同步状态：`pending` `syncing` `synced` `sync_failed`
- 主题状态：`unused` `queued` `used`

### 关键边界
- `completed` 不等于 `synced`
- 同步失败时主题不会恢复为 `unused`
- 删除中断任务时才会走释放占用逻辑
